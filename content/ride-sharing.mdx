## Problem

This is the backend for an Uber-style ride-hailing app, built as a Go microservices course project. The web client, architecture docs and deploy README come from the course starter; the Go services, messaging, tracing and Kubernetes wiring are the author's.

## Architecture diagram

```text
Groups
  RabbitMQ: exchange trip, dlx: queues

Flow
  web (starter Next.js) --(HTTP + WebSocket)--> api-gateway
  api-gateway --(gRPC)--> trip-service
  api-gateway --(gRPC)--> driver-service
  trip-service --(HTTP)--> OSRM routing API
  trip-service --> MongoDB
  api-gateway <--> queues
  trip-service <--> queues
  driver-service <--> queues
  payment-service <--> queues
  payment-service --(Checkout Session)--> Stripe
  api-gateway ..(traces)..> Jaeger
```

The web client reaches the api-gateway over HTTP and WebSocket. The gateway calls trip-service and driver-service over gRPC, and the trip lifecycle (driver request, accept or decline, payment session) moves as events through one RabbitMQ topic exchange. The diagram shows one tracing edge; all four Go services export traces to Jaeger.

## Key decisions

- **gRPC for request/response, RabbitMQ for the trip lifecycle.** Preview, create-trip and driver registration are gRPC calls (`proto/trip.proto`, `proto/driver.proto`); everything after trip creation is an event published on the `trip` exchange (`shared/messaging/rabbitmq.go`). The event design is in the course docs.
- **Dead-letter exchange with retries.** Every queue is declared with `x-dead-letter-exchange=dlx`, and consumers retry with backoff before rejecting (commit `2b38298`, `shared/retry/retry.go`). The headers set before rejection are not republished, so the end-to-end dead-letter path is wired but not verified.
- **Trace context carried through AMQP headers.** A custom publisher and consumer propagate it, so one Jaeger trace spans HTTP, gRPC and the queue hop (`shared/tracing/rabbitmq.go`, commit `db48438`).
- **Layered trip-service with a repository interface.** `internal/{domain,service,infrastructure}` has in-memory and MongoDB implementations of `TripRepository`; MongoDB was swapped in last (commit `7342c0e`).
- **Stripe behind an interface.** `domain.PaymentProcessor` hides the Stripe adapter in `services/payment-service/internal/infrastructure/stripe/stripe.go`.

## Challenges

- Several fixes came from wiring services together: a mis-named proto field (`e7293be`), a WebSocket route (`1b56f7e`), RabbitMQ consumer error handling (`7de98eb`) and Mongo env vars (`3fac848`).
- Driver and WebSocket state live in per-process memory while driver-service runs two replicas in dev (`infra/development/k8s/driver-service-deployment.yaml`). A code comment in `connection_manager.go` notes that multiple gateways would need shared storage.
- `tilt up` needs `infra/development/k8s/secrets.yaml`, which is gitignored and not documented, so a fresh clone cannot start without creating it.

## Results

The Go code builds and passes `go vet` (checked on a copy with Go 1.24.7). In code, the flow covers route preview with four fare tiers via an external OSRM service, fare storage in MongoDB, trip creation, driver matching, driver accept or decline over WebSocket, and Stripe Checkout session creation. Matching picks the first registered driver with the same package, and driver location updates are ignored.

The payment loop is not finished: there is no Stripe webhook or success handling, so a trip is never marked paid. MongoDB is used only by trip-service. There are no tests and no CI. The production manifests and GCP deploy steps are from the starter and cover only the gateway and trip-service, so no deployment is claimed here.
